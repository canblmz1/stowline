## Change and automated checks

Source: `9491ef718882260d1aa431113591931975e9a36b` on
`fix/operator-recovery-chain`, [draft PR #1](https://github.com/canblmz1/stowline/pull/1).

The registered SCM handler verifies recovery before invoking the startup callback.
That callback runs the existing guard/counter/file-swap logic before config,
secrets, engine initialization or normal/background work. Rollback and subsequent
application-initialization failures hand off using an ordered Running channel
notification, synchronous `SetServiceStatus(Running)`, then abnormal exit.
This prevents a late StartPending notification from overwriting the handoff and
keeps recovery valid with `qfailureflag=FALSE`. Recovery configuration/read-back
errors are visible and stop application startup; interactive `service run` never
reconfigures the installed service.

This exit choice follows the documented distinction between crash recovery and
[non-crash failure recovery](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/ns-winsvc-service_failure_actions_flag).
No failure-action flag or host-wide timeout change is needed.

Tests execute the production `Service.Execute`, actual startup callback and
real guard/files, including ordering, no work on rollback, boot count before
fallible initialization, recovery failure, interactive isolation and synchronized
handoff. Existing healthy-update, corrupt-artifact and identity tests remain.
Independent read-only review found and verified correction of both the status
ordering race and initialization-error exit/recovery mismatch.
